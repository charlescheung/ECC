# 代码审查

对未提交的更改进行全面的安全性和质量审查：

1. 获取更改的文件：`git diff --name-only HEAD`

2. 对每个更改的文件，检查：

**安全问题（严重）：**

* 硬编码的凭据、API 密钥、令牌
* SQL 注入漏洞
* XSS 漏洞
* 缺少输入验证
* 不安全的依赖项
* 路径遍历风险

**代码质量（高）：**

* 函数长度超过 50 行
* 文件长度超过 800 行
* 嵌套深度超过 4 层
* 缺少错误处理
* `console.log` 语句
* `TODO`/`FIXME` 注释
* 公共 API 缺少 JSDoc

**最佳实践（中）：**

* 可变模式（应使用不可变模式）
* 代码/注释中使用表情符号
* 新代码缺少测试
* 无障碍性问题（a11y）

3. 生成报告，包含：
   * 严重性：严重、高、中、低
   * 文件位置和行号
   * 问题描述
   * 建议的修复方法

4. 如果发现严重或高优先级问题，则阻止提交

绝不允许包含安全漏洞的代码！

## 步骤 5 — 追加上线计划

审查报告生成后（无论结论如何），扫描 `docs/` 下的设计文档，向每个符合条件的文件末尾追加上线计划章节。

**文档识别规则**：文件名或顶级标题包含 `prd`、`adr`、`spec`、`design`、`architecture`、`runbook`、`plan` 的 `.md` 文件视为设计文档。排除 `README.md`、`CHANGELOG.md`、`CONTRIBUTING.md`、`CLAUDE.md`、`SECURITY.md`。跳过 frontmatter 中 `status: Deprecated` 的文件，以及已包含 `## 上线计划` 或 `## Release Plan` 章节的文件。

**向每个符合条件的文档末尾追加以下内容：**

```markdown
## 上线计划
**状态**：准备发布
**发布日期**：{YYYY-MM-DD}
**分支**：{当前分支名}

### 发布范围
{1-3 句话，来源于文档的功能描述}

### 上线前检查清单
- [ ] 所有单元测试和集成测试通过
- [ ] 代码评审已批准（无 CRITICAL 或 HIGH 问题）
- [ ] 安全扫描通过
- [ ] 质量门控为绿色
- [ ] 设计文档状态已更新为 `Approved`
- [ ] 数据库迁移脚本已在预发环境审查并测试
- [ ] 生产环境变量和密钥已配置
- [ ] 接口变更已通知下游依赖服务（如有）

### 部署步骤
1. 最终审批通过后，将 PR 合并到 `master`
2. CI/CD 流水线自动触发，监控构建和测试阶段
3. 部署到预发环境，执行冒烟测试
4. 验证关键指标和日志（错误率、延迟、CPU/内存）
5. 部署到生产环境（蓝绿发布或滚动发布）
6. 对生产环境接口执行上线后冒烟测试
7. 监控 30 分钟，关注错误告警和监控大盘

### 回滚方案
- **触发条件**：部署后 30 分钟内错误率 > 1% 或 P95 延迟超过基线 2 倍
- **处理方式**：回退合并提交或重新部署上一个镜像版本

### 上线后验证
- [ ] 生产环境冒烟测试通过
- [ ] 错误率和延迟无明显上升
- [ ] 关键业务流程已手动验证（2-3 个核心路径）
- [ ] 值班工程师已知晓，上线后监控 30 分钟
- [ ] 上线统计文档已更新发布说明

### 相关人员
| 角色 | 负责人 |
|------|--------|
| 发布负责人 | {git config user.name} |
```

输出已更新和已跳过的文件列表。
